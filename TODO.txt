[ ] P2  Iterator<T> 高级类型（与当前 IterSemType 整合）

      - 缺：是否引入新 SemType 还是依赖接口结构匹配（建议先做接口扩展）

GC 缺失功能清单（基于 2026-07-18 重新核验 runtime/gc.h + gc.cpp）
----------------------------------------------------------------

[-] P2  精确栈扫描（替代保守扫描）  [2026-07-18 暂不实施]
      - 现状：[gc.cpp:243-262](runtime/gc.cpp#L243) markPhase 中 stackRoots_
        采用"保守扫描"——按 sizeof(void*) 对齐扫描栈内存，把候选指针
        当作 GcObject* 检查是否在 page 范围
      - 暂不实施原因：P0 完成后 CodeGen 已为 GC 指针类型的局部变量生成
        GcRootHandle 包装（精确注册到 roots_），协程帧也由 GcRootHandle
        精确扫描。stackRoots_ 的保守扫描仅作协程帧兜底（GcRootHandle 在
        协程挂起期间的行为依赖协程实现细节，保守扫描是安全网）。
        实际影响小：协程帧内大部分对齐数据是 GcRootHandle::ptr_ 字段，
        本来就是 GC 指针；desc/size 验证会跳过非 GC 对象。
      - 远期改进：若 profiling 显示内存占用过高，再做精确扫描

[x] P2  compactAndReclaim 的存活检测性能优化  [2026-07-18 完成]
      - 改造：用 std::map<const char*, Page*> 建立 page.data 有序索引，
        upper_bound 二分查找归属 page，O((n+m) log n)
      - 文件：runtime/gc.cpp:584-646
      - 验收：5000 次迭代压力测试通过，GC 无 crash

[~] P2  TLAB（Thread-Local Allocation Buffer）  [2026-07-18 延后]
      - 现状：bumpAlloc 是全局单线程的（currentPage_ + bumpOffset）
      - 缺：多线程并发分配需要每线程独立 TLAB，避免锁竞争
      - 延后原因：当前 sync_thread_plan.md 尚未实施，无多线程分配压力。
        待 sync_thread 完成后再做
      - 前置：先实现多线程 GC 暂停（已完成 P1 §八）

[-] P2  GC 触发策略调优  [2026-07-18 暂不实施]
      - 现状：kYoungThreshold=256KB, kOldThreshold=1MB（写死）
      - 暂不实施原因：当前无配置系统（ConfigDecl 未实现），环境变量方式
        价值有限。默认阈值在 Aura 当前规模下足够用
      - 远期改进：待 Aura 配置系统完善后再做
      - 设计：参考 plan/plan-syncmode.md 的 ConfigDecl 机制

[~] P2  对象可移动性（compacting GC）  [2026-07-18 延后]
      - 现状：compactAndReclaim 只回收整页，不搬运对象
      - 缺：mark-compact 算法，存活对象拷贝到新页，消除碎片
      - 影响：实现后需要转发指针（forwarding pointer）+ 更新所有引用
      - 延后原因：风险过高（需更新所有引用：roots / stack / fields /
        array 元素），compactAndReclaim 已能回收空页，碎片问题不严重
      - 风险：高复杂度，涉及 GcRootHandle / stackRoots 的更新

[ ] P3  分代年龄记录
      - 现状：promoteToOld 一次晋升到老年代
      - 缺：对象年龄（survival count），多次 minor GC 后才晋升
      - 设计：GcObject 加 uint8_t age 字段，默认 age=2 晋升

[ ] P3  并发 GC（concurrent marking）
      - 现状：GC 全程 stop-the-world
      - 缺：mark 阶段并发执行，仅 sweep 阶段暂停
      - 风险：需要读屏障/写屏障配合，极复杂

[ ] P3  Large Object Space（大对象区）
      - 现状：大对象（如长 GcString）和小对象共用同一 page
      - 缺：大对象独立分配，避免 page 碎片
      - 设计：> 32KB 的对象直接从 OS 分配，独立追踪

[ ] P3  GC 日志与统计
      - 现状：gcCount/minorGcCount 已记录但无输出
      - 缺：GC 事件日志（暂停时间、回收字节、晋升数量），
        可通过 #gc.verbose = true 开启

GcString 优化（基于 plan/gcstring_optimization.md，2026-07-18 评估）
分阶段：第一阶段不依赖 GC，可立即做；第二阶段需 GC 真正运行
----------------------------------------------------------------

[ ] P1  GcString::empty() / from(bool) / from(int) 静态缓存  [第一阶段]
      - 现状：每次 from(bool) 都分配 5 字节字符串；from(int) 每次 snprintf+alloc
      - 缺：empty() 返回全局单例；from(bool) 返回 "true"/"false" 单例；
        from(int) 缓存 -128~127
      - 风险：静态局部变量线程安全（C++11 起保证，但 Aura 协程模型需确认）
      - 文件：runtime/builtin/string.h, runtime/builtin/string.cpp
      - 详见：plan/gcstring_optimization.md §三 Step 1

[ ] P1  concat_multi 运行时支持  [第一阶段]
      - 现状：[string.cpp:66-75](runtime/builtin/string.cpp#L66) concat 每次分配+memcpy
      - 缺：新增 concat_multi(initializer_list<const GcString*>) 一次性分配
      - 文件：runtime/builtin/string.h, runtime/builtin/string.cpp
      - 详见：plan/gcstring_optimization.md §三 Step 2

[ ] P1  CodeGen 识别链式 string + string 脱糖为 concat_multi  [第一阶段]
      - 现状：[ExprGen.cpp:254](src/CodeGen/ExprGen.cpp#L254) 生成
        aura_rt::concat(aura_rt::concat(aura_rt::concat(a, b), c), d)
        3 次分配 + 中间对象 memcpy 2 次
      - 缺：genBinaryExpr 检测 BinaryExpr(Plus, ...) 链，≥3 个操作数时
        脱糖为 aura_rt::concat_multi({a, b, c, d})
      - 风险：链中混入非 string 类型（s + 42 + t）需 fallback 到 concat
      - 文件：src/CodeGen/ExprGen.cpp:235-265
      - 详见：plan/gcstring_optimization.md §三 Step 3
      - 收益：a+b+c+d 从 3 次分配+6 次 memcpy → 1 次分配+1 次 memcpy

[ ] P2  GcString 加 capacity 字段 + reserve/make_with_capacity API  [第二阶段]
      - 前置：先做 GcStringBuilder 类型
      - 现状：[string.h:27](runtime/builtin/string.h#L27) 仅 length，无 capacity
      - 缺：int32_t capacity 字段；data() 偏移要改；
        TypeDescriptor.size 需更新（仍 ptrFieldCount=0）
      - 文件：runtime/builtin/string.h, runtime/builtin/string.cpp
      - 详见：plan/gcstring_optimization.md §三 Step 4

[ ] P2  GcStringBuilder 类型（可变字符串缓冲区）  [第二阶段]
      - plan/plan13.md 规划
      - 现状：无此类型
      - 缺：新类型支持 append + to_string；与 concat_multi 整合
      - 前置：先做 capacity 字段
      - 文件：runtime/builtin/string_builder.h (新增)

[ ] P2  GcString 子串共享（零拷贝 slice）  [第二阶段]
      - 前置：GC 真正运行 + parent 字段加入 ptrFieldOffsets
      - 缺：GcString 加 parent + offset 字段；新增 slice(start, len) 方法
      - 风险：parent 必须被 GC 正确扫描，否则悬空指针
      - 文件：runtime/builtin/string.h, runtime/builtin/string.cpp
      - 详见：plan/gcstring_optimization.md §三 Step 5

[ ] P2  GcString 哈希缓存  [第二阶段]
      - 前置：引入 Map<K, V> 类型（当前无）
      - 现状：string 当 map key 时每次重新计算 hash
      - 缺：mutable uint32_t hash 字段，懒计算
      - 当前收益：0（无 Map 类型）
      - 文件：runtime/builtin/string.h

[ ] P3  GcString Rope 表示  [远期]
      - 前置：profiling 显示拼接是热点
      - 缺：树形节点（left/right GC 指针 + length）；
        c_str() 时扁平化；== 比较需重写
      - 风险：架构级重构，影响所有 string 操作
      - 文件：runtime/builtin/string.h
      - 详见：plan/gcstring_optimization.md §二 C1

[-] P3  GC 暂停期 interning  [不可行]
      - 前置：GC 真正运行 + mark 阶段可遍历所有对象
      - 当前：GC roots_ 为空，markPhase 无法工作
      - 结论：推迟到 GC 完全落地后再考虑

[-] P3  单引用原地修改（is_unique）  [不可行]
      - 前置：GC 配合检测引用数 或 引入引用计数
      - 当前：无引用计数机制
      - 结论：推迟到引入引用计数后
