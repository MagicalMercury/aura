你最终采用的写法是正确且地道的修复。下面我把这个 bug 的来龙去脉彻底拆解清楚。

## Bug 根源：协程帧与 lambda 闭包的生命周期割裂

### 原始代码回顾

```cpp
for (auto id : ids) {
    tasks.push_back([=]() -> task {
        std::cout << "spawn id=" << id << std::endl;
        co_return;
    }());
}
```

这里的执行流程可以分成三个阶段：

1. **创建 lambda 闭包对象**  
   `[=]` 按值捕获了当前的 `id`，闭包内部有一个 `int id;` 成员。

2. **立即调用 lambda，创建协程**  
   lambda 调用时，协程开始执行，先运行到 `initial_suspend()`（你设为了 `suspend_always`），然后立即挂起，返回 `task` 给 `push_back`。此时**协程的第一段代码（`co_await initial_suspend()` 之前）已经运行完毕，但协程体的业务代码一行都还没跑**。

3. **临时 lambda 闭包对象析构**  
   lambda 是临时对象，在本条语句结束时销毁。`id` 成员随之消亡。

问题就出在第 2 步：编译器在处理 **lambda 内定义的协程** 时，并不会把按值捕获的 `id` 深拷贝到协程帧里。  
C++20 协程的状态机中，协程帧需要保存“将来恢复时需要访问的所有非局部数据”。对于普通函数，参数和局部变量会自动进入协程帧；但对于 **lambda 闭包中的成员变量**，编译器惯用的实现方式是：  
**在协程帧里只保存一个指向闭包对象的 `this` 指针，访问 `id` 时实际变成 `this->id`**。  
这意味着协程体中的 `id` 完全依赖外部闭包对象的存在。一旦闭包先于协程恢复而销毁，`this` 就是野指针，访问 `this->id` 就是未定义行为。

为什么打印出三个 `99`？  
循环变量 `id` 在栈上反复使用同一个地址（或寄存器），临时闭包对象也可能复用相近的内存位置。三次循环结束时，栈上那块内存里最后写入的值正好是 `99`。三个协程恢复后全都用悬垂指针读到了这个残留的 `99`，表现出“看起来像是最后的值被捕获了三次”的现象。

### 为什么“协程内拷贝”没用？

```cpp
tasks.push_back([=]() -> task {
    int my_id = id;          // ❌ 依然无效
    std::cout << "spawn id=" << my_id << std::endl;
    co_return;
}());
```

很多人会直觉地认为，把 `id` 赋给一个局部变量 `my_id`，`my_id` 是协程帧的一部分，应该就安全了。  
但要注意：**`int my_id = id;` 这行代码的执行时间点是协程恢复（`resume()`）之后**。  
在恢复之前，协程帧里确实为 `my_id` 预留了空间，但它的初始化表达式 `id` 仍然要去访问闭包对象。闭包对象早已销毁，所以这一赋值本身就是从野指针读值，行为已未定义。即便之后 `my_id` 存活在协程帧里，读到的值也已经是垃圾。

因此，**局部变量拷贝没有把数据的“获取时机”提前到协程创建时，只是把悬垂访问推迟了一行，根本无法根治。**

## 正确修复：让数据在协程创建时就进入协程帧

你最终采用的方案：

```cpp
for (auto id : ids) {
    tasks.push_back([](int id) -> task {
        std::cout << "spawn id=" << id << std::endl;
        co_return;
    }(id));
}
```

这里的关键变化是：**`id` 不再是闭包捕获的成员，而是 lambda 的形参，通过 `(id)` 立即传入**。

### 为什么会安全？

C++20 协程标准明确规定，**协程的形参必须在协程帧中保存独立的副本**。编译器会在协程帧创建时，自动把参数值拷贝/移动到帧内。整个过程发生在协程第一次挂起之前，与闭包生命周期无关。

时间线如下：

1. 创建 lambda 临时对象（无捕获或空捕获，没有生命周期依赖）。
2. 调用 `operator()(id)`，形参 `id` 被初始化为循环变量的值。  
3. 进入协程体，编译器生成协程帧，**此时就把形参 `id` 的值拷贝到协程帧内部**。  
4. 执行到 `initial_suspend()`，协程挂起，返回 `task`。  
5. lambda 调用结束，形参 `id` 和 lambda 临时对象都析构，**但协程帧内的副本完好无损**。  
6. 后续 `resume()` 恢复协程时，访问的是协程帧内的独立副本，完全是安全的。

这个修复方案同时解决了两个核心问题：

- **数据存放位置正确**：副本在协程帧里，生命周期与协程一致。
- **数据捕获时机正确**：在协程创建时就已经保存，不依赖任何外部对象的存活。

### 另一种等效写法：普通函数

你也可以直接使用普通函数，让参数传递更为直观：

```cpp
task coro(int id) {
    std::cout << "spawn id=" << id << std::endl;
    co_return;
}

for (auto id : ids) {
    tasks.push_back(coro(id));
}
```

这和你采用的 lambda 传参在底层语义上完全一样——参数在创建协程帧时被拷贝。很多人偏爱普通函数，因为它彻底规避了 lambda 闭包带来的心智负担。

---

## 总结：协程与 lambda 的正确组合原则

| 写法 | 数据何时进入协程帧 | 是否安全 |
|------|-------------------|----------|
| `[=]() -> task { ... }()` | 不进入，只存 `this` | ❌ 悬垂 |
| `[=]() -> task { int x = id; ... }()` | 恢复时才从 `this->id` 读，太晚 | ❌ 悬垂 |
| `[](int id) -> task { ... }(id)` | **协程创建时拷贝参数** | ✅ 安全 |
| `coro(id)` （普通函数） | **协程创建时拷贝参数** | ✅ 安全 |

核心思想一句话：**需要跨越挂起点的数据，必须作为协程形参或协程体创建前的局部变量来传递，不能依赖 lambda 捕获的隐式 this 指针。**
