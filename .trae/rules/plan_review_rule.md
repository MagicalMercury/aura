# Plan 文件审查规则（Plan Review Rule）

> 适用对象：`plan/` 文件夹下的所有草案文件（含 `change.md` 合并实施文档）
> 触发时机：任何 plan 文件进入“待审查”状态时，必须执行本规则

## 1. 审查流程总览

1. **读取 plan** → 提取“受影响的文件和模块列表”及“修改步骤”中的所有文件路径与行号。
2. **定向分发** → 针对每个涉及的**具体文件**，按需启动 Search Agent 子代理检索该文件的当前源码（含上下文）。
3. **逐项比对** → 对每个修改步骤，将 plan 中的“修改前/后”代码与实际源码比对，验证准确性。
4. **全链路评估** → 结合检索到的调用关系、依赖、测试用例，完成风险分析。
5. **输出报告** → 按固定格式输出审查结论。

## 2. 定向检索分发

### 2.1 触发条件

* **只有当 plan 中明确列出某批文件路径（如** **`src/CodeGen/StmtGen.cpp`）或者是某个重要的Phase以及Agent认为值得且必须搜索时**，且该文件将在“修改步骤”中被更改时，才对该文件或该 Phase 启动 Search Agent。

* 如果 plan 未涉及某文件，则绝不搜索，避免无效检索。

### 2.2 检索范围

针对每个被列出的文件，Search Agent 必须检索以下内容：

* 该文件当前仓库中**完整最新内容**，至少包含修改点所在函数/类的全部代码。

* 若修改涉及函数调用（如新增调用 `genRecordToViewIIFE`），需一并检索被调用函数的**声明位置**和**定义位置**（如 `CodeGen.h` 和 `StmtGen.cpp` 中的定义）。

* 若修改涉及宏、trait 或模板特化，需检索相关头文件（如 `variant.h`）。

* 若修改涉及 `example/test.aura` 新增用例，需检索该文件当前内容以确定插入位置。

### 2.3 禁止行为

* **不得**因某个文件未在列表中而自行臆测其内容。

* **不得**凭训练记忆描述任何源码片段，必须引用实际检索到的内容。

* **不得**泛化搜索整个代码库，除非 plan 明确提到“影响构建系统”或“影响全局头文件”。

## 3. 审查内容要求

### 3.1 代码修改的绝对溯源原则

* 针对 plan“修改步骤”中的每个 **修改前/修改后** 代码块，审查者必须：

  1. 引用 Search Agent 检索到的当前源码片段（附文件路径+行号）。
  2. 指出 plan 中描述的修改前代码是否与实际一致；若不一致（行号偏移或内容变化），标记为 ⚠️。
  3. 验证修改后代码的语法正确性（特别是模板、宏、偏移计算等）。
  4. 若新增函数/方法，检查其所有调用点是否已在 plan 中列全。

### 3.2 全链路理解（End-to-End）

必须从以下维度独立分析，并引用源码证据：

| 维度        | 检查项                                                 |
| --------- | --------------------------------------------------- |
| **构建依赖**  | 改动是否影响 CMakeLists.txt？是否需要新增源文件或链接库？                |
| **运行时接口** | 修改后的 runtime 函数签名是否与编译器生成的调用代码匹配？                   |
| **测试覆盖**  | `example/test.aura` 中的新增用例是否覆盖了所有改动路径？是否存在未覆盖的边界场景？ |
| **异常与回退** | plan“风险与应对”中的每项缓解措施是否具体可操作？是否有后备方案？                 |

### 3.3 已知限制评估

* 对 plan“已知限制”部分逐条评估其是否可接受、是否影响合入、是否有后续计划。

## 4. 审查报告输出格式

```markdown
# Plan 审查报告：[plan 文件名]

## Search Agent 检索摘要
- **检索文件列表**：[列出所有实际检索的文件，每个文件附带最近一次 commit hash 或修改时间（可选）]
- **关键源码定位**：
  | 文件 | 定位的行号区间 | 当前源码片段摘要（仅必要部分） |
  | ---- | -------------- | ------------------------------ |
  | ... | ... | ... |

## 源码映射审查
| 步骤 | 文件 | 比对结果 | 备注 |
| ---- | ---- | -------- | ---- |
| 步骤 1 | `runtime/builtin/iterator.h` | ✅ 一致 / ⚠️ 行号偏移 / ❌ 内容不符 | ... |

## 全链路风险分析
- **构建系统**：[无风险 / 需调整 CMake / 阻塞]
- **Runtime 兼容性**：[通过 / 需同步修改 runtime 代码 / 阻塞]
- **测试覆盖**：[覆盖完整 / 缺少某类用例 / 阻塞]
- **异常与回退**：[可接受 / 需补充应对措施]

## 已知限制评估
- [逐条结论：可接受 / 需纳入后续计划 / 应在本 plan 解决]

## 最终裁决
- [ ] 通过（Approve）
- [ ] 需修改（Changes Requested）— [列出具体修改点]
- [ ] 驳回（Rejected）— [理由]

```

## 附则：

* 本规则适用于所有 plan/ 下的草案及 change.md 合并文档。

* 若审查过程中发现 plan 引用的文件路径或行号与实际不符，必须在报告中明确指出，并建议更新 plan。

* 任何未执行定向检索即输出的审查结论，视为无效，需重新执行。
