## 代码编辑时规则：

### 1. 创建新代码：
 - **必须**在编辑代码前完整阅读相关 API 文档和现有代码，对代码架构有全貌理解。
 - **必须**遵循最小化改动原则，只添加必要的代码。
 - **禁止**使用不存在或未验证的 API。如果不确定某个 API 是否存在，必须先通过搜索或阅读源码确认。
 - **禁止**凭记忆或假设编写代码。所有类型、函数名、参数签名必须与实际代码一致。
 - **必须**确保新增代码与现有代码风格一致（命名规范、缩进、注释风格等）。
 - **必须**为复杂逻辑添加必要的注释，解释意图而非实现细节。

### 2. 修改代码：
 - **必须**在修改代码前完整阅读相关 API 和上下文代码，理解修改的影响范围。
 - **必须**遵循最小化改动原则，只修改必要的部分。
 - **必须**验证修改不会破坏现有功能。如果涉及公共 API 或接口变更，需要评估影响范围。
 - **禁止**删除或修改不确定用途的代码。如有疑问，先通过搜索或询问确认。
 - 如果修改涉及以下情况，**必须**生成修改 Plan 并等待批准：
   - 重构代码结构（如拆分函数、合并模块、改变架构）
   - 修改公共 API 或接口签名
   - 修改核心逻辑（如 GC、协程调度、类型系统）
   - 修改超过 5 个文件或单个文件超过 250 行
 - Plan 内容必须包含：
   - 修改目标与原因
   - 受影响的文件和模块列表
   - 修改步骤（分阶段描述）
   - 可能的风险与应对方案
   - 测试验证方案

### 3. 代码质量要求：
 - **必须**保持代码可读性：函数名清晰表达意图，避免过度缩写。
 - **必须**控制函数复杂度：单个函数不超过 50 行，嵌套不超过 4 层。超出时考虑拆分。
 - **必须**避免重复代码：相同逻辑出现 3 次以上时，考虑提取为公共函数。
 - **必须**正确处理错误：所有可能失败的操作必须有错误处理（返回错误、抛出异常或显式忽略并注释原因）。
 - **禁止**在代码中硬编码魔法数字或字符串。使用常量或配置。
 - **必须**在修改后运行相关测试（如有）或手动验证关键功能。

### 4. 禁止事项：
 - **禁止**凭猜测使用 API 或库函数。
 - **禁止**在未理解代码逻辑的情况下修改或删除代码。
 - **禁止**引入未声明的依赖或未验证的外部库。
 - **禁止**提交包含语法错误或类型错误的代码。
 - **禁止**在修改后跳过验证步骤直接提交。
