[ ] record 直接调 next()（p.next()，p 为 record 变量非 Iterator 视图）未支持：有标注 Sema 放行 → 坏 C++
    - 2026-08-29 修复「Iterator 视图直接调 next()」时确认（独立既有缺口，与视图 next 不同源）：
      `let p: Point = {...}; p.next()`（Point 为普通 record）→ inferMethodCall record 分支在
      typeMethods_ 找不到 next（next 是字段/接口方法，非该 record 方法）→「未匹配到方法 → 保持
      放行」（CallInfer.cpp record 分支，对照 map/filter/collect 的「record 直调报错（v1 不支持）」
      路径不同）→ 返回 ErrorSemType：
      - 有标注 `let r: Optional<Point> = p.next()` → **Sema 放行**，CodeGen 生成 `p->next()`
        → g++ `'struct Point' has no member named 'next'`（坏 C++，实测 2026-08-29）。
      - 无标注 `let r = p.next()` → Sema 报误导性干净错误 `cannot infer element type from
        initializer`（G4 兜底，报错文本像空列表错误，未引导用户转视图）。
    - 影响：record 上误写 next()（或想用迭代器协议）得不到干净「record 'Point' has no method
      'next'」报错；有标注直接坏 C++。
    - 修复方向：inferMethodCall record 分支未匹配方法时，对「该 record 未声明的方法名」报 E013
      干净错误（`record type 'Point' has no method 'next'`，仿接口/内置分支），并提示正确用法
      （`let it: Iterator<Point> = p` 转视图后调 next / 或实现 next 方法）；不得静默放行。
    - 状态：调研完成（待修复）

[ ] decideCoro 一遍扫描顺序依赖：外层（函数/方法）调用后置声明的协程函数/方法 → 传播失败 →
    调用点不 co_await → task 析构不执行体 → 协程体静默不执行
    - 2026-08-29 实现方法协程化时实测发现（独立既有缺口，函数侧 CallExpr 传播同样受限）：
      ```aura
      fun outer(io: Io) { runner2(io) }        // runner2 声明在后面
      fun runner2(io: Io) { io.println("r2") } // 协程（io 异步）
      ```
      → outer/outerM 不被标为协程（decideCoro 按声明顺序逐个判定，扫描时 coroutineFunctions_
      尚无后置声明的 runner2）→ outer 内 `runner2(io)` 不 co_await → task 立即析构
      （~task() handle_.destroy()，initial_suspend=suspend_always 从未 resume）→ 协程体静默
      不执行（实测仅输出 main done，无 runner2 ran / helperM ran）。
    - 根因：CodeGen.cpp 一遍循环，decideCoro 依赖已插入的 coroutineFunctions_ 传播；声明顺序
      颠倒时信息不足。无编译错误（静默错误，更难排查）。
    - 修复方向：decideCoro 判定改为固定点迭代（多轮扫描 coroutineFunctions_ 直至稳定，限制轮数
      防死循环），或对依赖做拓扑排序；亦可在 genCallExpr / genMethodCall 对「调用已标协程的
      被调用者但当前非协程上下文」报编译错误（防静默）。
    - 状态：调研完成（待修复）

[ ] 泛型方法体 `return []`（函数类型元素列表）生成 `Array<T>::make(0)`（方法声明侧 CodeGen）
    - 2026-08-28 验证「泛型 record 方法返回类型调用点代换」时发现：泛型 record 方法
      `fun (self Runner<T>) getTransforms() throws -> [Transform<T>] { return [] }` → 方法体
      生成 `Array<T>::make(0)`（应为 `Array<Transform<T>>::make(0)`）→ g++ cannot convert
      'Array<int>*' to 'Array<std::function<int(int)>>*'。对照：非泛型函数 return [] →
      `Array<std::function<int32_t(int32_t)>>::make(0)` 正确；record 元素 [Node<T>] return []
      正确（mapSemType 产出 "Node<T>*" 不含 auto）。
    - 根因：genListExpr 空列表分支（ExprGen.cpp）inferredType 推断元素类型，元素为函数类型别名
      FuncSemType（Transform<T>）且方法体泛型（T 未实例化）时 mapSemType 产出含 "auto" 的 C++
      类型被 G4 拦截 → 落 currentTParams_[0] 兜底 `Array<T>::make(0)`，与返回类型不匹配。
    - 修复方向：空列表兜底改用 currentReturnCppType_（方法/函数声明返回 C++ 类型）提取
      Array<...> 元素类型生成 make(0)（仿 let 空列表由目标类型取元素），而非硬编码 currentTParams_[0]。
    - 状态：调研完成（待修复）

[ ] int/float/bool 值类型（变量/函数调用返回值）上调用方法（如 to_string）被 Sema 放行 → 坏 C++
    - 2026-08-29 验证 M4 时发现：`let x = 42; x.to_string()` / `get42().to_string()` → Sema 静默

      genMethodCall access 判定对值类型接收者默认 `->`（valueTypeVarNames_ 不含 int）。
    - 修复方向（推荐 ①）：Sema 对 int/float/bool 的未注册方法报 E013 干净错误（typeKey 扩到
      int/float/bool，或 PrimSemType 分支查 BuiltinRegistry 无命中即报错，对齐 string 路径）；
      ② 若设计支持 int.to_string() 等则注册 + CodeGen 生成转换（runtime/types.cpp 已有）+ access
      对值类型接收者用 `.`。
    - 状态：调研完成（待修复）

[ ] 泛型 record 类型实参为 record 时，方法体/字面量实例化路径 T 未补 *（gc_alloc<Box2<Rec5>> vs 返回 Box2<Rec5*>*）
    - 2026-08-28 修泛型接口适配器时发现（独立于适配器，非接口场景同崩）：`type Box2<T> = {
