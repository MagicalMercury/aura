## Go 语言使用 APC 的对比（核心问题）

**答案是：是。Go 在 Windows 上正是用 `QueueUserAPC` 做线程异步抢占**，Unix 上用信号（`tgkill` + SIGURG）。但 Go 的用法与本 plan 有**四个本质差异**：

| 维度 | Go（1.14+ 异步抢占） | 本 plan |
| ---- | ---- | ---- |
| **Windows 中断** | `preemptM` → `QueueUserAPC(apc_preempt, mp.thread, 0)`，callback 执行**实际抢占** | `QueueUserAPC(空操作)` 仅打断 alertable wait |
| **Unix 中断** | `signalM` → `tgkill(getpid(), tid, SIGURG)` | `pthread_kill(SIGUSR1)` |
| **handler 行为** | `doSigPreempt`：检查安全点 → **改写信号上下文 PC/SP** → 重定向到 `asyncPreempt`（保存寄存器、进入调度器） | 空 handler，只靠 EINTR 打断阻塞 |
| **能否中断 CPU 密集** | ✅ 能（`asyncPreempt` 由编译器在函数序言/回边注入，信号把执行流硬切到安全点） | ❌ 明确放弃（plan §1.4 承认需 P3+ 编译器支持） |
| **信号选择** | SIGURG——**特意避开 SIGUSR1/SIGUSR2**（用户库常用，避免冲突） | SIGUSR1，未讨论与用户信号冲突 |
| **信号风暴防护** | `atomic.Cas(&mp.signalPending, 0, 1)` 合并——同线程只发一次信号 | 每 20ms 无合并重发 |

**结论**：方向一致（用 OS 原语打断线程缩短 STW 等待），但 Go 的机制更完整——空操作 handler 只能打断"阻塞等待中的线程"，Go 能打断"运行中的 goroutine"。plan 的 P3+ 规划（编译器注入 poll 点）正是 Go 的 `asyncPreempt` 路线，两者可衔接。

## 全链路风险分析

- **构建系统**：需新增 2 个源文件 + 2 个平台文件进 CMakeLists（plan §13 Step 6 已给出，✅ 正确），无其他问题。
- **Runtime 兼容性**：⚠️ 有细节问题，需修正后再合入：
  1. **无谓词 wait_for 下信号收益被高估**（plan §4.3）：当前 `all_stopped_cv_.wait_for(lk, 50ms)` 是**无谓词版**——被 EINTR 打断后 glibc/libstdc++ 内部重试**继续等**，外层 while 才查 `stopped_threads_`。信号对 cv wait 实际无帮助（真正唤醒靠 notify_all）。plan 表格"✅ EINTR → 重检查谓词"不成立。
  2. **SIGUSR1 冲突**：用户代码/库可能占用 SIGUSR1。建议改用 SIGURG（Go 同款选择）。
  3. **alloc.cpp L148 Marking 期等待**：该处等待的是"Marking 结束"，非"STW 通知"——中断后立即重试仍 Marking，无意义，还增加忙轮询。建议排除在替换清单外。
  4. **Windows 上收益主要来自 100μs 轮询而非 APC**（plan §11 自己承认）——需明确定位：APC 只解决 sleep 类阻塞，cv/sem 仍靠轮询。
  5. **EventLoop 缺口未覆盖**：plan 未提 task.cpp 主线程 10ms IOCP 轮询不响应 STW（cv 化 plan 阶段 2.2 内容）。
  6. 线程句柄生命周期（§6.3/§10.3）：ESRCH/无效句柄忽略处理 ✅ 正确。
- **测试覆盖**：§15 覆盖功能/性能/安全三类，但测试路径为外部 Linux 环境（§13 Step 7），需改写为本仓库流程（compile.cmd + test.aura + verify_gc_log.ps1），并补充"中断风暴"（高频 broadcastInterrupt）与"信号与用户 SIGUSR1 共存"用例。
- **异常与回退**：`AURA_INTERRUPT_SAFEPOINT` 编译宏回退 ✅ 合理，但建议改为运行时开关（编译宏需重编）。
