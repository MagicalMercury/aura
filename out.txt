   ⇒ 70µs 后**第二个 initiator 进场**。

### 2.2 根因（已确证）

**一次 GC 事务被释放了两次**：
- `safepoint()` 的收尾（旧 `L248`）写 `gc_in_progress_ = false`
- `startConcurrentGc()` 内部（旧 `L573`）**也**写 `gc_in_progress_ = false`

而 `startConcurrentGc()` 只是同一事务的**中段**。于是出现「**已释放但事务未结束**」的窗口 ⇒ 下一个/第三个线程趁窗口抢到 initiator ⇒ **两个 initiator 并存**，各自等对方停靠，而 initiator 不自计数 ⇒ `stopped_threads_` 封顶 `threadCount-2` ⇒ **永远差 1** ⇒ 死锁。

> 一句话：**`L573` 是"果"，`L248` 是实际放行通道，"差 1"才是因。**

### 2.3 修法（`runtime/gc/safepoint.cpp`，728 → 759 行，diff +34/−3）

1. `startConcurrentGc()` 清理段**删除** `gc_in_progress_.store(false)` —— **释放权归调用方**
2. 新增 TU 局部 `static std::atomic<unsigned> g_gc_owner_tid`：抢到 initiator 时登记自己；释放点校验持有者，**非持有者释放为 no-op**
3. **未改 `gc.h`**（令牌为 TU 局部）；**未做 initiator 自计数**、**未改 `waitForRootThreadsStopped` 的 target**、**未调阈值**

### 3.3 🎯 最终定位：机制分析（读代码后的推理链）

**核心链条（我的判断）**：

1. `intern_string` 返回的对象由 `g_internPool` 里的 `GcRootHandle<GcString*>`（scope = **`GcRootScope::Global`**）保活。
2. **Global 根的注册形态**（`handles.h:32-41`）：
   ```cpp
   GcRootHandle(T val, GcRootScope scope) : ..., val_(val), mode_(ValueGlobal) {
       ptr_ref_ = reinterpret_cast<GcObject**>(&val_);   // 根指向 handle 内部值
       GcHeap::instance().registerGlobalRoot(ptr_ref_);  // 进 globalRoots_ 容器
   }
   ```
   池里的 handle 由 `std::make_unique<GcRootHandle<GcString*>>(...)` 创建 ⇒ **handle 在普通堆（非 GC 页）**。
3. **compact 的三条更新路径**（我逐一核过代码）：
   - **步骤 1**（thread-local handle，`compact.cpp:330-337`）：**有** `isGCAddress` 防御（bug-79 L2 加固）✅
   - **步骤 3**（`globalRoots_`，`compact.cpp:342-354`）：
     ```cpp
     std::memcpy(&obj, rootPtr, sizeof(GcObject*));
     if (obj && obj->forwarded()) { ... }   // ⚠️ 直接解引用 obj，无 isGCAddress 防御
     ```
     ⇒ **有 `forwarded()` 判断，理论上能更新**；但**缺 `isGCAddress` 防御**（与步骤 1 不对称）—— 若 `*rootPtr` 已是悬垂值，这里就是**未定义行为**（潜在二次崩溃点，独立加固项）
   - **`relocateGlobalRootPtrs()`（方案 P，`compact.cpp:433`）**：只处理「`rootPtr` 落在 `compactEntries_` 某个被搬运对象的 `[old, old+size)` 区间内」的情形。**intern 池的 handle 在普通堆、不属于任何 GC 对象 ⇒ 不适用（正确跳过）** ✅
4. **关键推论**：既然 handle 不被搬运，池值就**只能靠步骤 3 更新**。而事实 #6 显示「池值 = 崩溃时的坏值、从未更新」⇒ **只能是 `obj->forwarded()` 当时为假**。
5. **`forwarded()` 为假的两种情况**：
   - (i) 对象**没被本次 compact 搬**（⇒ 值本来就该保持，不构成崩溃）
   - (ii) **对象早已被回收、页已释放** ⇒ `obj->forwarded()` 读的是**垃圾内存** ⇒ 返回 false ⇒ 值永久失效 ❌❌
6. ⇒ **指向 (a)：对象在**更早某轮 GC** 被回收了 —— 也就是说**池的 Global 根在某条路径上没起作用**。
7. **它为什么没起作用？** 候选机制（按可能性排序）：
   - **★ A3（首选）**：**标记期新注册的 Global 根未被重扫**。首次 `intern_string("t_")` 会**分配对象 + 注册 Global 根**；若注册发生在**扫根之后**（并发标记进行中），该对象**本轮不被标记** ⇒ 若它只被这个新根引用 ⇒ **被回收**。这正是 SATB/并发标记必须覆盖的「新根写入」缺口（SATB 管的是「引用被覆盖」，而「新根注册」是另一类）。
   - **A1**：注册/注销竞态 —— 析构用 `unregisterGlobalRoot(ptr_ref_)`（**`std::find` 精确匹配**，`roots.cpp:151-154`）⇒ 多线程下若匹配失败 ⇒ 残留悬垂或误删。
   - **A2**：扫根循环（`mark_sweep.cpp:128-129`）与 `registerGlobalRoot` 并发 ⇒ 遍历期间 `globalRoots_` 变化 ⇒ 漏扫。
8. **调和「崩溃依赖 compact」这个对照实验**：禁 compact 时**页不会被真正释放** ⇒ 悬垂地址**仍可读**（读到毒值但不崩）；一旦 compact 释放旧页 ⇒ 该地址**不可读** ⇒ SIGSEGV。⇒ **「禁 compact ⇒ 不崩」并不说明"compact 弄坏了值"，而是"compact 让悬垂变得致命"** —— 这与 (a) 完全自洽。
9. **v4 的"gdb 下零 compact 完成也崩"**：与 #8 表面矛盾，但 v4 自己标注了 **gdb 扰动**（Heisenbug 下时序不同）⇒ **该观察不可作为定案依据**，需**正常运行时**的手段印证。

### 3.4 剩余待证点（就是主人要的那"最后一块拼图"）

**判定 (a) 还是 (b)，只需回答一个问题：**

> 崩溃时那个 intern 对象，**是被"回收"了（页已释放）**，还是**被"搬走"了（页面搬迁）**？

**最小实验设计（每一轮子 Agent 都没走到，我建议下一步做）**：
1. **正常运行时**（非 gdb）跑一次崩溃，在崩点用**最小干预**取 `parts` 的坏地址 `X`；
2. 查 `X` 是否落在 GC 页表/`freeMediumPages_` 等**已释放集合**内 ⇒ 若「已释放」⇒ **(a) 成立**；
3. 若 (a)：在 `mark_sweep.cpp:128-129`（扫根循环）下断点，看该池 handle 的 `val_` **是否被遍历到**；再在 `registerGlobalRoot` 下断点，看**注册时刻 vs 扫根时刻的先后** ⇒ 直接验证 A3；
4. 修法方向（按结论）：
   - 若 A3 ⇒ 在标记期注册新 Global 根时，**把新根推入标记工作队列/或触发重扫该根**（等价于对新根做 SATB 处理）
   - 若 A1 ⇒ 修注册/注销的匹配与并发（`std::find` → 稳定标识）
   - 若 (b) ⇒ 修 `compact.cpp` 步骤 3 的更新路径 + 补 `isGCAddress` 防御

### 3.5 一并发现的独立加固项（建议另行登记）

- **`compact.cpp:346-352` 的步骤 3 缺 `isGCAddress` 防御**（步骤 1 在 bug-79 L2 已加固，两者**不对称**）。若 `*rootPtr` 悬垂，`obj->forwarded()` 即为 UB。
- **`clear_intern_cache()` 的代次（gen）机制虽然方向正确，但实测无效**（`safepoint.cpp:128/:309` 都在 **GC 开始前** bump；在"bump 之后、compact 之前"填充的缓存会带着"代次相符"逃过作废）。**若最终保留 gen 机制，应在 compact 完成之后（`relocateGlobalRootPtrs()` 之后）再 bump 一次。**

## §九-1 已完成的定位工作（进展记录）

### 进展 1：读懂 `compact()` 主流程（`runtime/gc/compact.cpp:63-73`）

```cpp
void GcHeap::compact(CompactScope scope) {
    computeForwardingAddresses(scope);   // 1. 决定谁被搬（在旧位置置转发标记）
    if (compactEntries_.empty()) return;
    updateAllReferences(scope);          // 2. 更新所有根/引用（含步骤1 thread-local / 步骤3 globalRoots_）
    copyObjectsToNewLocations(scope);    // 3. 真正 memcpy 搬运到新页
    relocateGlobalRootPtrs();            // 4. 重定位"堆内 handle"的 &val_（方案 P）
    rebuildPageList(scope);              // 5. ★ 释放旧页：VirtualFree(page, 0, MEM_RELEASE) / munmap
}
```

**两条硬事实**：
1. **更新引用（步骤 2）发生在搬运（步骤 3）之前** —— 标准 forwarding 模式。
2. **`rebuildPageList` 会把旧页整个 `MEM_RELEASE`（unmap）**（`compact.cpp:237-243`，All 模式）。

**⇒ 这解释了 b2 的条件对照「禁 compact ⇒ 不崩」**：
禁 compact 时**页不会被真正释放** ⇒ 任何残留的旧地址**仍可读**（读到 free-fill 毒值 `0xeeffeeff` 但不 SIGSEGV）；
一旦 compact 走完 `rebuildPageList` ⇒ 旧页 unmap ⇒ **该地址不可读** ⇒ 崩溃。
**⇒ 结论：compact 不是凶手，`MEM_RELEASE`（unmap）才是处决者。** 这与「坏值指向旧堆布局地址（`0x190098`/`0x1a0098`，随 ASLR 变化）」完全吻合。

### 进展 4：⭐ 推出「**b3 的 gen 修复为何无效**」的确切时间线（关键）

b3 的修复是「全局代次 `g_internCacheGen` + 查找时校验」。它方向对（缓存确实存裸指针），但**时机错**：

1. GC 开始**前**，线程 W 到达 safepoint ⇒ 执行 `clear_intern_cache()`（`safepoint.cpp:128`）⇒ 清空自己的缓存 + **bump 全局 gen 到 G1**（W 自己的 `cache.gen` 仍是 G0）
2. W 在 safepoint 内后续路径（或 STW 前的窗口）再做一次 `intern_string` 查找 ⇒ 发现 `cache.gen(G0) != curGen(G1)` ⇒ 清空并把 `cache.gen` 置为 **G1** ⇒ **从池填充"正确"的值**（此时对象尚未搬，是旧地址，仍然有效）
3. STW ⇒ compact：`updateAllReferences` 更新池的值 → `copyObjectsToNewLocations` 搬运 → **`rebuildPageList` unmap 旧页**
4. W 恢复运行 ⇒ 再次查找 ⇒ `curGen` 仍是 **G1**，与 `cache.gen`（G1）**相等** ⇒ **缓存不作废** ⇒ 返回**旧地址**（已被 unmap）⇒ **SIGSEGV**

**⇒ 结论：代次必须在 compact 完成之后（`relocateGlobalRootPtrs()` 之后 / `rebuildPageList` 前后）再 bump 一次，否则"bump 之后、compact 之前"填充的缓存会带着"代次相符"逃过作废。**

**⇒ 待验证的疑点**：v4 曾用 gdb 报「池里存储的值 == 崩溃时的坏值」。若**池本身**也是坏的（而不只是缓存），则上述时间线只是**第二条**路径，还需要修 `updateAllReferences` 步骤 3。**这两个可能必须分开验证**（池 vs 缓存）。

### 下一步（主 Agent 计划）

2. 按结论二选一修复：
   - **若只有缓存坏** ⇒ 在 compact 之后补一次 gen bump（改动极小）

### ⚠️ 我必须修正一个方法论错误（写在此处立此存照）

§九-2 的结论「**池是好的**」下得**过早**：我的依据只是"池的值落在合理堆区间（`0x830xxx`）"，
**并没有在同一次崩溃里把它与 `parts` 的坏值做直接对比**。
——这与之前"方案 E"那次犯的错同类：**把"看起来合理"当成"已经证实"**。

**真正的判决性判据只有一个**：
> **在同一次崩溃现场**，看 `parts` 的坏值 `X` **是否等于**池里对应 key 的值。

## §九-8 ✅✅ **修复成功**：落点修正后 20/20 全绿

**改动（最终形态）**：`runtime/gc/compact.cpp` 的 `compact()` **末尾**（`rebuildPageList(scope);` 之后）加一行
```cpp
    clear_intern_cache();   // [FIX-B86-2] compact 完成之后作废所有线程的 L1 intern 缓存
```
并**撤掉** §九-4 那 2 处错误落点（核对：`safepoint.cpp` 与实验前**逐字节一致** `IDENTICAL ✅`）。
（`compact.cpp` 第 11 行本来就有 `#include "../builtin/string.h"`，无需新增依赖。）

**结果**：
| 判据 | 结果 |
|---|---|
| 形态② `p13_thread_compact` **20 轮** | **SIGSEGV=0 / rc0=20 / other=0** ✅（此前 100% 崩）|
| 程序是否**真跑完**（防"假通过"）| stdout = `p13_thread_compact start` + `p13_thread_compact end` ⇒ **完整执行** ✅ |
| 形态① `p13_noconcat` 20 轮 | **clean=20 / bad=0** ✅ 无回归 |

### 根因（确证：H-cache）

`intern_string` 的 **L1 线程局部缓存存的是裸指针**，而它的**作废时机错了**：
- `safepoint.cpp:128` 在 **GC 开始前** 调用 `clear_intern_cache()`（bump 全局代次）
- 线程若在该次 bump **之后、compact 之前** 填充过缓存，其 `cache.gen` 恰好等于当时的全局代次
- 随后 compact 搬走对象 + `rebuildPageList()` 用 **`MEM_RELEASE` 卸载旧页**
- 该线程恢复运行后，缓存**"代次相符"⇒ 逃过作废** ⇒ 返回**已卸载页上的旧地址** ⇒ `concat_multi` SIGSEGV

**⇒ 修法**：在 `compact()` **真正完成之后**再 bump 一次全局代次，使所有线程的缓存在下一次查找时整体作废，
从而**重新走 L2 全局池**取值 —— 而池是被 `updateAllReferences` **正确更新过**的（§九-6 已实测：池 `"t_"`=`0x80cd40`，坏值只在缓存）。

| 我的第一次（§九-3/§九-4）| 在 `safepoint.cpp` 的 `needCompactOnly` 分支 compact 之后补 bump | **该分支在实际路径中根本没被走到**（真正的调用点在 `mark_sweep.cpp` / `parallel_mark.cpp`）⇒ 等于没改 |
