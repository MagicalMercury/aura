## 一、方案 D：名字借用 → 模板参数绑定

### 1.1 机制（对照探针 2 的失败产物）

你探针 2 拿到的失败形态：
```cpp
struct __GcUClosure_0 final : aura_rt::CallableObjBase {
    template <typename U>
    aura_rt::Array<U>* operator()(aura_rt::Array<A>* items_raw,       // ← A 未声明
                                  aura_rt::CallableObj<U, A>* transform_raw) { ... }
};
```

**方案 D 的形态**：
```cpp
template <typename A>                                    // ← 唯一的新增：A 借用参数
struct __GcUClosure_0 final : aura_rt::CallableObjBase {
    Cap0 cap_0;                                           // 捕获槽照旧
    template <typename U>
    aura_rt::Array<U>* operator()(aura_rt::Array<A>* items_raw,
                                  aura_rt::CallableObj<U, A>* transform_raw) { ... }
};

// 创建点（makeM 模板方法体内，A 天然可见）：
auto* __o = aura_rt::gcConstruct<__GcUClosure_0<A>>(&__GcUClosure_0<A>::desc, ...);
```

### 1.2 为什么每个失败点都被解掉

| 失败点 | D 的消解 |
|---|---|
| struct 定义在 header，`A` 不可见 | `template <typename A>` 的 A 是**形式参数**（占位符），文件作用域合法——**它不引用外层，它等待外层绑定** |
| `A` 不能重声明（遮蔽 `-Wtemplate-body`）| 借用参数与 `currentTParams_` 剔除逻辑**兼容**：剔除的是「闭包自有声明」，D 只把被剔除的名字**收集后送进模板参数列表**——不声明两次 |
| operator() 签名要同时见 A 和 U | A = 类模板参数（嵌套名，整个 struct 范围可见），U = 成员函数模板参数——**都在 struct 自己的作用域内**，标准嵌套模板用法 |
| body 里 `let result: [U]`、`transform(item)` | A/U 作为类/函数模板参数在 body 可见，body 生成机制**零改动** |
| 实例化点 `gcConstruct<...>` 要完整类型 | 实例化点在 makeM 体内（模板方法，A 可见）→ `__GcUClosure_0<A>` 完整类型 ✓ |
| 调用方 `m.get()->operator()(items, transform)` | A 已固化在**对象类型**里，调用点只需推导 U（从 transform 实参）——推导链比你现在的形态还短 ✓ |

**语义同构性**：模板 lambda 对外层 A 是「名字借用」（不捕获，作用域可见）；D 把借用实现为「类模板参数 + 实例化点绑定」——**同一个语义的两种 C++ 载载**。这不是新发明，是 C++ 模板参数提升的惯用法，且与 F 既有机制同构——**Cap 参数本来就是「把捕获的类型送进 struct」，D 只是把「借用的名字也送进去」**。

**GC 安全**：A 是类型不是值，不进 desc；若闭包捕获 `self: Box<A>`，槽类型 `Box<A>` 在实例化点 A 可见，desc 复合偏移照旧。零新运行时机机制。

### 1.3 判据侧的落点

分流/收集逻辑改动（genGcUClosure + analyzeClosureGenerics 附近）：
1. 被剔除的泛型名**不再丢弃**——收集为**借用参数表**（按首次出现序，剔重）；
2. struct 模板参数列表 = `template <typename A?, typename Cap0, ...>`（借用参数在前或后，定一个顺序约定即可）；
3. 分流判据扩展：`callableParamIndices 命中 && ownGen`（你画像里的形态）→ F（带借用参数）——注意与 bug-83 已迁的「callableParamIndices 具体签名」路径**不打架**（那是 SemType 判据，具体形态照旧走 CallableObj）。

## 二、三问裁决

`CallableObj<R, P...>::__invoke` 是 `static R __invoke(...)` 函数指针槽——**创建点就要完整具体类型**，U 未绑定时无法实例化。**这正是当初 F 诞生的原因**（方案 B 与被否的「Callable 擦除返回」同死因：无穷 origins）。(A) 你的探针证否成立。(C) 是 D 失败后的退路，不是首选。
