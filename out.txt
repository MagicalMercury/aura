### A1. P0 `unionVariantGcUnsafe` 判定与 `isHeapSemType` 口径**不一致**

**位置**：plan §4.1 [L78-97](file:///d:/you/Aura/plan/联合类型GC安全问题.md#L78-L97)

**问题**：

`unionVariantGcUnsafe` 与 [ExprGen.cpp:12-30](file:///d:/you/Aura/src/CodeGen/ExprGen.cpp#L12-L30) `isHeapSemType` 对相同 SemType 的判断结论**会冲突**：

|------|--------------------------|----------------------------------|------|

### A3. P2a `desc->size` 读取点核对**遗漏了 alloc 路径**

**位置**：plan §4.2 [L145](file:///d:/you/Aura/plan/联合类型GC安全问题.md#L145)

**plan 声称**："`desc->size` 唯一读取点 mark_sweep.cpp:102（`== 0` 判定）不受影响；alloc 走显式 size 参数，不依赖 desc->size。"

**结论**：plan 描述准确，但核对不彻底（只查了 2 处）。建议 P2a 增加全量 `grep "desc->size"` 步骤。

### A4. P2b `dynamicDesc` 钩子遗漏 `updateInlineArrayElements` 与 `markInlineArrayFields`

**位置**：plan §4.3 [L149-167](file:///d:/you/Aura/plan/联合类型GC安全问题.md#L149-L167)

**问题**：

plan 只在 `markFields`（[mark_sweep.cpp:179](file:///d:/you/Aura/runtime/gc/mark_sweep.cpp#L179)）和 `updateObjectFields`（[compact.cpp:397](file:///d:/you/Aura/runtime/gc/compact.cpp#L397)）加 `dynamicDesc` 钩子。

**风险等级**：P2（次要）。

### A5. P1 `Variant::desc()` 缺失且与 `dynamicDesc` 关系不明

**位置**：plan §4.4 [L176-200](file:///d:/you/Aura/plan/联合类型GC安全问题.md#L176-L200)

**问题**：

plan 展示了 `descFor(i)` 和 `dynamicDesc`，但 `make_variant` 调用的是 `Variant<Ts...>::desc()`（[L196](file:///d:/you/Aura/plan/联合类型GC安全问题.md#L196)）：

```cpp
GcHeap::instance().alloc(sizeof(Variant<Ts...>), &Variant<Ts...>::desc()));
```

而 `Variant::desc()` **未定义**，只定义了 `descFor(i)`。且 `desc()` 应返回什么？

- 若返回"默认变体的 desc" → 分配时 storage_ 还未初始化，index_=0 → 返回 `kDescs[0]`（即第 0 变体的 desc）
- 但 `make_variant` 立即设置 index_ 后 `desc()` 仍返回第 0 变体 desc → 与实际变体不符

**正确做法**：alloc 用占位 desc（如 nullptr 或第 0 变体 desc），赋值后由 GC 通过 `dynamicDesc` 钩子读取真实 desc。

plan 没说清这个时序。建议明确：
- `Variant::desc()` 返回 `kDescs[0]`（占位）
- `dynamicDesc(obj)` 根据 `obj->index_` 返回对应 desc
- alloc 时 `desc()` 的作用仅是"占位让 GC 不误判为无 desc 对象"，实际扫描走 `dynamicDesc`

**风险等级**：P1（重要，影响实施）。

## B. 协程同步链栈深度保护.md 审查

### B1. `g_chainDepth` 只增不降设计**正确但描述有误导**

**位置**：plan §4.3 [L101](file:///d:/you/Aura/plan/协程同步链栈深度保护.md#L101)

> 不需要递减：栈解开时若递减会与归零冲突（第 256 层归零后，外层 255 层 resume 返回各自 `--` 会把计数打成负数）

**实际源码核对**：

[task.h:49-51](file:///d:/you/Aura/runtime/task.h#L49-L51) 现状：
```cpp
void await_suspend(std::coroutine_handle<>) noexcept {
    if (continuation) continuation.resume();
}
```

plan 改为：
```cpp
if (++g_chainDepth >= kMaxChainDepth) {
    g_chainDepth = 0;
    scheduleOnEventLoop(continuation);
} else {
    continuation.resume();
}
```

**问题分析**：

"第 256 层归零后，外层 255 层 resume 返回各自 `--` 会把计数打成负数"——这个描述**只在采用递减方案时才成立**。plan 选择不递减，所以这个"冲突"本身不存在。描述是"解释为什么不递减"，但读起来像"递减方案有 bug"。

**实际真正的风险**（plan 未提）：只增不降 → **每次 EventLoop 顶层 resume 都从 0 开始**，但如果 EventLoop::processReady 内 batch 循环 resume 多个协程（[task.cpp:103-106](file:///d:/you/Aura/runtime/task.cpp#L103-L106)），每个 resume 是新链，但 `g_chainDepth` 不重置——**只有归零后才重置**。

例如：
1. processReady resume 协程 A，A final resume B，B final resume C，g_chainDepth=3
2. C 完成，g_chainDepth 仍为 3
3. processReady resume 协程 D（新链），D final resume E，g_chainDepth=5
4. E 完成，g_chainDepth=5
5. ... 累积到 512 触发 scheduleOnEventLoop

**后果**：多个独立短链被错误视为一个长链，提前触发 scheduleOnEventLoop。plan §4.3 [L101](file:///d:/you/Aura/plan/协程同步链栈深度保护.md#L101) 说"无害（多一轮队列，语义等价）"，✓ 正确。但**建议在文档中明确**：g_chainDepth 是"线程级累计 final 恢复次数"，不是"当前链深度"。

**风险等级**：P2（描述清晰度）。

### B4. `final_awaiter::await_suspend` 改造未考虑 `noexcept` 语义

**位置**：plan §4.1 [L71-79](file:///d:/you/Aura/plan/协程同步链栈深度保护.md#L71-L79)

**问题**：

```cpp
void await_suspend(std::coroutine_handle<>) noexcept {
    if (!continuation) return;
    if (++g_chainDepth >= kMaxChainDepth) {
        g_chainDepth = 0;
        scheduleOnEventLoop(continuation);   // 可能抛？
    } else {
        continuation.resume();               // 可能抛？
    }
}
```

现状 [task.h:49-50](file:///d:/you/Aura/runtime/task.h#L49-L50) 标 `noexcept`。`scheduleOnEventLoop` → `EventLoop::schedule` → `std::lock_guard<std::mutex>` + `std::queue::push`，**push 可能抛 `std::bad_alloc`**。在 `noexcept` 函数中抛出 → `std::terminate`。

**建议**：
- `scheduleOnEventLoop` 内 try/catch 吞掉异常（日志记录，不传播）
- 或 plan 明确"schedule 失败 = OOM，terminate 可接受"

**风险等级**：P1（重要，OOM 场景崩溃行为变化）。

### B5. `thread_local` 跨静态库/可执行链接**未实际验证**

**位置**：plan §9 [L166](file:///d:/you/Aura/plan/协程同步链栈深度保护.md#L166)

> `inline thread_local` 跨静态库/可执行文件单定义合并 | C++17 inline 语义保证；单 TU 内测试先行

**问题**：

Aura runtime 是静态库 `libaura_rt.a`（[AGENTS.md](file:///d:/you/Aura/AGENTS.md) 构建 runtime/build）。`inline thread_local` 在静态库 + 主可执行文件链接时，**MSVC/MinGW 可能产生多个符号副本**（不同编译器对 inline thread_local 的合并行为不一致）。

虽然 plan 说"C++17 inline 语义保证"，但 MinGW (UCRT64 g++) 实际行为需验证。如果 g_chainDepth 在静态库和主可执行中各有一份，则计数分裂，保护失效。

**建议**：plan §7 增加"先在单 TU 内验证计数正确，再全量链接 runtime 验证 g_chainDepth 地址唯一（打印 &g_chainDepth）"。

**风险等级**：P1（重要，平台特定）。

### B6. `when_all` 长列表**未实际触发保护**

**位置**：plan §5 [L107](file:///d:/you/Aura/plan/协程同步链栈深度保护.md#L107)

> `when_all`（task.h:190-195）串行 co_await 同样受益。

**问题**：

[task.h:190-195](file:///d:/you/Aura/runtime/task.h#L190-L195) `when_all` 实现：
```cpp
inline task<void> when_all(std::vector<task<void>> tasks) {
    for (auto& t : tasks) {
        if (t) co_await t;
    }
    co_return;
}
```

每个 `co_await t` → `t` 的 `final_awaiter::await_suspend` → continuation = when_all 协程 → `continuation.resume()`。

但 `when_all` 协程的 final 又恢复其 continuation（调用者）。**链结构**：
```
caller → when_all → t1 → when_all → t2 → when_all → ... 
```

每两层 `when_all → t_i` 之间，`t_i` final 恢复 `when_all`，`when_all` 恢复 `caller`（如果 when_all 已 co_return）。实际上 when_all 在 for 循环中 co_await，**final 恢复 caller** 只发生在 when_all 完成时。

**深度分析**：每个 `co_await t_i` 是独立链（t_i 的 final 恢复 when_all），不是长链。只有 caller → when_all 是一层。所以 when_all 长列表**不会**触发长链保护，plan 说"同样受益"**不准确**。

**建议**：plan §5 修正描述："when_all 内部每个 `co_await t` 是短链（深度 1），不触发保护；但 when_all 自身的 final 恢复 caller 是一层，无长链风险"。

**风险等级**：P2（描述不准确）。

# D. 迭代器 × GC 交互崩溃发现（issue 记录，待研究）

> 提出时间：2026-08-05
> 状态：**暂停修复**，转为 issue 供用户仔细研究后完成。
> 相关文件：`example/iter_gc_test.cpp`（手工测试，change.md §6.5）、`runtime/builtin/iterator.h`、
> `runtime/gc/gc.h`、`runtime/gc/compact.cpp`。

## D.1 现象

`iter_gc_test.exe` 运行 `test_chain_gc_pressure` 时崩溃（0xC0000005）：
- 迭代中途触发 `forceGc()`（mark-sweep + compact）后，root 的 `fit`（`FilterIter*`）变量被改写为 **vtable 地址**，
  下次 `fit->next()` 调用空/错位 vtable → 段错误。
- 并非偶尔：只要 GC 发生 compact 且迭代器链存活，必然复现。

## D.2 根因（已定位）：多继承布局违反 GC 核心假设

**GC 核心假设**：`GcObject*` 地址 == 堆对象起始地址（offset 0）。
`GcRootHandle` 的 `ptr_ref_` 指向用户变量地址，GC 直接按 `GcObject*` 读写该地址（[gc.h](file:///d:/you/Aura/runtime/gc/gc.h) 中
`markPhase`/`updateAllReferences` 均如此）。

**C++ 多继承布局**：`struct FilterIter : GcObject, Iterator<T>` 中，
- `Iterator<T>`（含虚函数 `virtual next()`）成为 **primary base**，排在 **offset 0**（放 vptr）；
- `GcObject` 子对象被排到 **offset 8**。

于是：
1. `fit`（`FilterIter*`）首 8 字节是 **vptr**，不是 `desc`；
2. GC 按 `GcObject*` 读 `fit` → `obj->desc` 实际读到 **vptr**；
3. `markObject`/`markFields` 按错误 desc 偏移扫描 → 标记错位；
4. compact 的 `setForwardingPtr` 把 `fit` 变量更新成 forwardingPtr → `fit` 变成 vtable 地址；
5. 用户代码再调 `fit->next()` → 0xC0000005。

### 插桩证据（已删除，记录如下）

```
fit dump: 30 f6 ab 3d f7 7f 00 00 | 80 f4 ab 3d f7 7f 00 00
           └ offset 0-7  = vtable 0x7ff73dabf630
             offset 8-15 = 真实 desc 0x7ff73dabf480
[DBG-mark] root %p -> obj=0x...00d0 desc=0x7ff73dabf630   ← GC 把 vptr 当 desc 读
[DBG-upd]  root %p: 0x...00d0 fwd -> 0x7ff73dabf630        ← fit 被更新成 vtable 地址
```

## D.3 影响范围

- 所有多继承 `GcObject` 派生对象（内置迭代器 `RangeIter/MapIter/FilterIter/FuncIter`）在 GC 下**全部不安全**，
  不限于 compact，mark-sweep 的字段扫描也已错位。
- 迭代器链一旦作为 GC 根存活且触发 GC，即崩溃或静默内存损坏。
- 阻塞 change.md §6.5「迭代器 × GC 交互测试」（0 泄漏 0 悬垂）验收。

## D.4 当前代码状态（探索性修改，未完成、未验证）

以下修改是为定位/尝试修复而加的，**保留在工作区作为 issue 起点**，不属于本轮提交：

| 文件 | 修改内容 | 结论 |
| ---- | ---- | ---- |
| `runtime/builtin/iterator.h` | `Iterator<T>` 加 `kGcSize=16` + `fromGc/toGc` 布局转换；`MapIter/FilterIter` 加 `srcGc_` 字段，desc 偏移改用 `offsetof(Self, srcGc_)`；`next()` 经 `srcGc_` 恢复接口指针；`make_map/make_filter` 用 `isGCAddress` 判定内置/适配器源；`collect_all` 加 GcRootHandle 保护链顶端 + 结果数组 | **未解决崩溃** |
| `runtime/gc/gc.h` | `isGCAddress` 声明 | 配套 |
| `runtime/gc/compact.cpp` | `isGCAddress` 实现（遍历小/中/大页 data 区） | 配套 |

**失败原因**：根因是 `GcObject` 子对象不在 offset 0（多继承下偏移更深）。
`toGc(src)` 反推的"对象起始"实际是 vptr 所在地址，`srcGc_` 记录的仍不是对象真实起始；
GC 对 `srcGc_` 字段的扫描同样错位。即：**只要 `GcObject*` ≠ 对象起始，任何"字段记录 + 扫描"修补都治标不治本**。

## D.5 候选修复方案

- **方案 A（推荐）**：给 `GcObject` 加 `virtual ~GcObject() = default;`，使 `GcObject` 成为 primary base 回到
  offset 0，恢复「对象起始 == `GcObject*`」假设，迭代器多继承布局自动正确。
  代价：所有 GC 对象 +8 字节 vptr（对象头 16 → 24）。
- **方案 B**：迭代器改为单继承 `GcObject`，内部持有接口指针/纯虚接口拆为单独 vtable 结构；
  代价：迭代器类层次重写（CodeGen 桥接 `make_range/make_map/make_filter/collect_all` 调用点同步调整）。
- **方案 C**：GC 支持「对象头偏移」记录（TypeDescriptor 加 headOffset，所有 `obj->desc` 读取点先换算真实头）；
  代价：GC 全量改造，侵入面最大，不建议优先。
